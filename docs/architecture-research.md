# Observability component research

Accessed 2026-11-11. Sources below are official project documentation/source or the Grafana dashboard catalog. This is a compatibility and design review, not a security audit.

## Recommendations

- Use `martin-helmich/prometheus-nginxlog-exporter` when request count, response/request bytes, and access-log-derived request/upstream latency are needed. Pin an explicit release, validate the config at startup, and standardize metric names across app namespaces with `metrics_override` plus `namespace_label` (for example `app`). The repository documents v1.9.2 packages, supports files and syslog, multiple namespaces and custom/relabelled labels. Its latency summary needs the corresponding NGINX log variables (`$request_time` and/or `$upstream_response_time`); configure the same fields in both NGINX `log_format` and exporter parser. The upstream is publicly active, but its visible README/release references alone do not establish a support SLA, so pin and assess release cadence before production adoption. [Exporter README](https://github.com/martin-helmich/prometheus-nginxlog-exporter/blob/master/README.adoc) · [Releases](https://github.com/martin-helmich/prometheus-nginxlog-exporter/releases)
- Treat `nginxinc/nginx-prometheus-exporter` as complementary: OSS NGINX `stub_status` supplies aggregate connection/request counters and gauges, not per-route request latency or app labels. NGINX Plus API exposes richer metrics. Label targets in Prometheus for instance/app identity. [Exporter source/docs](https://github.com/nginx/nginx-prometheus-exporter) · [NGINX stub_status semantics](https://nginx.org/en/docs/http/ngx_http_stub_status_module.html)
- For logs, use Grafana Alloy `loki.source.file` → optional `loki.process`/`loki.relabel` → `loki.write`. Persist Alloy's `--storage.path` so file offsets survive restarts; use stable, low-cardinality labels (e.g. `service_name`, `environment`, `host`), and keep request IDs, client IP, and raw URI out of indexed labels. Prefer JSON access logs and parse fields at query time/processing. Promtail is EOL as of 2026-03-02; migrate existing setups to Alloy. [Alloy file source](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.file/) · [Alloy→Loki](https://grafana.com/docs/loki/latest/send-data/alloy/) · [Loki labels guidance](https://grafana.com/docs/loki/latest/get-started/labels/) · [Promtail EOL notice](https://grafana.com/docs/loki/latest/send-data/promtail/)
- For a new Loki install, use single-binary/monolithic mode for a small deployment, filesystem storage only for a disposable/local setup, and object storage plus `store: tsdb`, `schema: v13`, `index.period: 24h` for durable production. Set `schema_config.configs[].from` to a past date for a new install. Existing installations must preserve their historical schema entries and add a future-dated schema when migrating; do not replace old schema history. Enable retention via compactor and explicitly set retention/tenant limits to fit policy. Split query frontend/querier/scheduler only as scale requires. Query dashboards with selective stream labels and tight time windows; Loki indexes labels, not log-line contents. [Storage schema](https://grafana.com/docs/loki/latest/operations/storage/schema/) · [Configuration](https://grafana.com/docs/loki/latest/configure/) · [Query best practices](https://grafana.com/docs/loki/latest/query/bp-query/) · [Deployment modes](https://grafana.com/docs/loki/latest/get-started/deployment-modes/)

## Metric semantics and dashboard compatibility

| Component/dashboard | Semantics and fit |
|---|---|
| `nginx-prometheus-exporter` | OSS metrics come from `stub_status`: accepted/handled connections and total requests are counters; active/reading/writing/waiting connections are gauges. Active includes idle/waiting. There are no request-time or upstream-latency metrics in the OSS stub-status exporter. NGINX Plus uses its API and exposes richer families. This is the right source for connection saturation and aggregate traffic, not per-app latency. [Exporter metric reference](https://github.com/nginx/nginx-prometheus-exporter#exported-metrics) · [NGINX field definitions](https://nginx.org/en/docs/http/ngx_http_stub_status_module.html) |
| `martin-helmich/prometheus-nginxlog-exporter` | Parses each access-log entry and emits counters/summaries by `method` and `status`; metric namespaces are configurable per app. Upstream timing is summarized in seconds when `$upstream_response_time` is logged. It supports labels from log fields, so avoid unbounded values (URL, IP, user agent); normalize routes using relabel matching and whitelist any categorical labels. [README metrics and relabeling](https://github.com/martin-helmich/prometheus-nginxlog-exporter/blob/master/README.adoc#collected-metrics) |
| Dashboard 17452 | Official NGINX exporter dashboard in the Grafana catalog, sourced from `nginxinc/nginx-prometheus-exporter`'s `grafana/dashboard.json`, Prometheus datasource, last catalog revision 2022-11-21. It targets the nginxinc metric family; use with OSS nginxinc exporter (or Plus-compatible corresponding series), not the access-log exporter's differently named metrics. Verify datasource variable and exporter version against imported JSON. [Catalog entry](https://grafana.com/grafana/dashboards/17452-nginx/) · [Exporter dashboard JSON](https://github.com/nginx/nginx-prometheus-exporter/blob/main/grafana/dashboard.json) |
| Dashboard 25257 | Catalog entry is “Nginx Log Exporter Dashboard”, Prometheus datasource, by rohitpotato, last updated 2026-05-06. It is the relevant candidate for access-log-derived exporter metrics, but the catalog metadata alone does not prove compatibility with this project's exporter metric prefix, labels, or histogram/summary representation. Inspect the downloadable JSON and map its PromQL to the chosen exporter; don't assume it works unchanged. [Catalog entry](https://grafana.com/grafana/dashboards/25257-nginx-log-exporter-dashboard/) |

### Practical metric design

Use the log exporter for request-level rates and latency distributions, nginxinc exporter for NGINX process/connection health, and Loki for search and forensic detail. Give each app a stable low-cardinality `app`/`service_name`; use normalized route labels only if bounded, and retain raw path/client/request ID in logs. Do not combine counters from both exporters into a single “requests” panel because they represent distinct collection pipelines and may count differently. In PromQL, calculate rates from counters and use histogram quantiles only if the metric is a histogram: the exporter's default `http_response_time_seconds` family is a summary, while the separately enabled `http_response_time_seconds_hist` family is a histogram and supports aggregatable percentile estimates. This lab enables the latter with explicit buckets.

## Source notes

- Grafana Alloy file source persists per-file offsets in its configured data path; removed targets lose their position entry, and re-adding a target starts from the beginning. Choose target discovery/restart behavior deliberately to avoid duplicate or skipped history.
- Loki defaults emphasize low-cardinality indexed labels; structured metadata requires TSDB/v13. Avoid indexing high-cardinality log attributes.
- The nginxinc exporter scrapes one or more NGINX endpoints, exposes `/metrics`, and Prometheus scrapes the exporter. The `stub_status` page itself is intentionally a compact server-wide view.
